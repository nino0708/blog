# pro-doc-design：プロに近い資料を作る

見た目と構成の判断はこのスキルで行い、ファイル操作の細部（XMLの注意点など）は
`anthropic-skills:pptx` / `xlsx` / `pdf` を併用する。根拠と出典は `references/principles.md`。

## 道具（scripts/）

| ファイル | 役割 |
|---|---|
| `setup.sh [作業フォルダ]` | BIZ UDゴシック・LibreOffice Impress・pptxgenjs・BudouX など足りない道具を入れる |
| `deck_kit.js` | pptxgenjs の部品集。テーマ、表紙、本文、表、図解パターン（帯・判断フロー・ステップ・カード・数字・注目帯・ロードマップ）、保存。`style: "cloud"` で下のスタイルになる |
| `cloud_art.js` / `plain_art.js` | 各スタイルの表紙・本文の背景（cloud＝雲・回路、plain＝緑の円弧） |
| `jp_wrap.py` | 文節（BudouX）と実フォント幅で改行位置を決める。`d.txt(..., { wrap: true })` から自動で呼ばれる |
| `finalize_pptx.py` | テーマに配色と日本語フォント（ea / Jpan）を書き込む。`d.save()` が自動で呼ぶ |
| `add_motion.py` | フェードの画面切り替えと、`b<番号>|` 名の図形の段階表示を付ける |
| `render.sh deck.pptx` | 検証 → PDF → ページ画像 → 埋め込みフォント確認 → 重複チェック |
| `redundancy_check.py` | 同じ言い回しが複数ページに出ていないか（くどさ）を調べる |
| `examples/sample_plain.js` | `style: "plain"` の見本（A4横5ページ）。**新しい資料はまずこれを複製して始める** |
| `examples/sample_cloud.js` | `style: "cloud"` の見本（濃紺・雲と回路。にぎやかにしたいとき） |
| `examples/sample_deck.js` | 白地のシンプルな見本（A4横6ページ・BIZ UDPゴシック）。かしこまった資料向け |

## 作り方の流れ（この順を崩さない）

### 1. ヒアリング：作る前に聞く
`AskUserQuestion` で、1回にまとめて聞く（最大4問）。聞かずに作ると作り直しになる。
- **使い方**：発表で見せる／PDFを配って読む／両方。文字量がまったく変わる（下の表）。
- **読み手と目的**：誰に、読んだあと何をしてほしいか（承認・理解・興味を持つ）。
- **形式と向き**：pptx / xlsx / pdf、A4横・16:9・A4縦。
- **ボリューム**：ページ数か発表時間（発表なら1ページ1.5〜2分が目安）。

「任せる」と言われたら：A4横・発表＋PDF配布・`style: "plain"`（全部ゴシック：Noto Sans JP＋Inter）。
社外向けで白地・Windows標準の書体が求められるときだけ、白地のスタイル（BIZ UDPゴシック・`navy`）にする。

## 見た目のスタイル
- **`style: "plain"`（既定）**：緑1色の濃淡・白地・ゴシック・左端の縦帯。装飾は控えめ。
  1色でも見やすくするため「濃い面は1ページ1か所、淡い面はまとまり、白＋枠はふつう、文字は黒に近い灰」と濃淡の役割を決めている。
  仕様は **`references/style-plain.md`**（「濃淡の使い分け」を必ず守る）。
- **`style: "cloud"`**：濃紺の帯＋淡い青の面＋白いカード＋雲と回路。にぎやかで IT らしい。仕様は `references/style-cloud.md`。
  どちらも骨組みは同じ（帯のタイトル＝目次の項目名、その下に「POINT」にそのページで伝えたいことを1文）。
  どちらにするか迷ったら plain。cloud は「IT・クラウドらしく派手に」と頼まれたときだけ。
- 白地（`style` なし）：白い背景＋結論タイトル。印刷前提・かしこまった資料向け。

| 使い方 | 文字量 | 本文の大きさ（A4横） | 作り方 |
|---|---|---|---|
| 発表で見せる | キーワード中心。3秒で要点がわかる | 18pt以上 | 話す内容はノートへ |
| PDFを配って読む | 文で書く。読むだけで意味が通る | 13〜16pt | 図解＋短い文 |
| 両方 | 結論タイトル＋短い文 | 14〜18pt | 動きは発表用、最終状態で完結させる |

### 2. 構成案（ゴーストデッキ）を先に見せる
デザインを始める前に、次の3つをテキストで作り、`AskUserQuestion` の preview で見せてOKをもらう。
1. **各ページの結論タイトル（1文）**：タイトルだけを上から読んで話が通じること（アクションタイトル）。
2. **ページごとの図解の型**：比較→表・2軸、手順→ステップ、時間→帯、判断→分岐フロー、量→グラフ（`references/layout-patterns.md`）。
3. **事実の置き場所表**：どの事実をどのページに書くか。**同じ事実は1か所だけ**。ほかのページでは「①」「→P.4」と参照する。

構成の型：結論を先に（ピラミッド）→ 全体像 → 詳細 → 次の行動。導入は状況→問題→解決（SCQA）。

### 3. 生成する
- PowerPoint：`examples/sample_cloud.js`（または `sample_deck.js`）を複製し、`deck_kit.js` の部品で組む。詳細は `references/layout-patterns.md` と `references/style-cloud.md`。
- 目次を置くときは、本文の帯のタイトルを目次の項目名と完全に同じにする。
- Excel：`references/excel.md` の規則と雛形で openpyxl を使って作る。
- 動き：`references/motion.md`。発表で使うページだけ、話の順に段階表示（`build: true`）。

### 4. 確認する（毎回・全ページ）
`bash scripts/render.sh out.pptx` を実行し、出力されたページ画像を**全部**見る。
下の「納品前チェック」に1つでも当たれば直して再実行する。

### 5. 渡す
- `.pptx`（編集用）と `.pdf`（配布用）を渡す。最終PDFはPowerPointで書き出すよう案内する。
- 報告は短く：変えたこと、**推測で補った箇所（要確認）**、残った作業（氏名の記入など）。

## デザインの原則（要点）

**構成**
- 1ページ1メッセージ。タイトルは名詞ではなく結論の文にする（例：「売上推移」→「売上は3年で2倍に伸びた」）。
- 非冗長：同じ内容を2回書かない。リード文がタイトルの言い換えなら書かない。
- 数字には必ず単位（「2」ではなく「2案件」）。根拠のない数字は書かない。

**見た目（ノンデザイナーの4原則）**
- 近接：関係するものは近づけ、無関係なものは離す。余白で区切り、線や枠は最小限。
- 整列：すべての要素を見えない縦線・横線にそろえる。余白（外周0.5インチ以上）と間隔（0.25〜0.3インチ）を全ページで統一。
- 反復：同じ種類のページは、タイトル位置・色・形を全ページでそろえる。
- コントラスト：目立たせるのは1ページに1か所。大きさ・太さ・色の差ははっきり付ける。

**視線の流れ（主役を決める）**
- 人の目は左上から入り、大きい・濃い・色の付いたものから順に見る（Z字：左上→右上→左下→右下）。
- 各ページで主役（最初に見てほしい1点）を1つだけ決め、左上に一番大きく・色付きで置く。ほかは小さく・控えめに。
- 同じ大きさのカードを並べると、どこから見ればよいか分からなくなる。主役のカードだけ大きさか色を変える。
- 白い面が多いと締まりがない。背景は淡い色面にし、白いカード（角丸＋薄い影）を浮かせる（Material Design 3 の考え方）。

**文字**
- 和文はゴシック体。cloud は Noto Sans JP＋Inter、白地は BIZ UDPゴシック（Windows 10以降の標準）。書体は1〜2種類まで。
- 見た目に凝るなら `createDeck({ font: "Noto Sans JP", latinFont: "Inter" })`（Googleの書体。数字と英字が締まる）。PDFには埋め込まれるが、pptxを編集するPCには無料フォントの導入が必要と伝える。
- 行間は文字の1.2〜1.5倍。太字は本物の太字がある書体で。
- 改行は文節で。`wrap: true` を使うか、自分で `\n` を入れる。単語の途中で折れたら必ず直す。
- 図形に対して文字が小さすぎる（スカスカ）のは失敗。図形を中身に合わせて小さくするか、文字を大きくする。

**色**
- ベース（白・薄いグレー）＋メイン（濃紺など）＋アクセント1色。アクセントは「ここを見て」の所だけ。
- 色だけで区別しない（色覚の多様性）。必ず文字ラベル・形・位置と組み合わせる。赤と緑の対比は避ける。
- 文字と背景のコントラストを十分に取る（本文の目安 4.5:1 以上）。

**図表・データ**
- 伝えたい点だけ色を付け、ほかはグレー。枠線・目盛り線・凡例は減らし、値は直接ラベルにする。
- グラフの作り方は `dataviz` スキルにも従う。

## このユーザー向けの約束（過去の指摘から）
- 構成・用途・向きは**作る前に質問する**。作ってから大きく直すのは避ける。
- 「くどい」は最も嫌われる。`redundancy_check.py` が出した重複は、参照に置き換える。
- 「スカスカ」もNG。図形の中の余白が文字の量より大きいときは詰める。
- 不自然な改行（「最新\n化」「時\n間」）はNG。実際に使う書体で書き出して確認する。
- 自慢に見える表現（「社内で一人だけ」など）は入れない。顧客名・取引関係（商流）は伏せる。
- 縦に並べた番号付きの一覧と、区分の色分け（例：定例／非定例）は好評。
- 飾りすぎは嫌われる（cloud を見て「飾りすぎ」）。一方、飾らなすぎも殺風景。色は1色の濃淡にし、飾りは円弧・縦帯など控えめな数点に絞る。
- 色を減らしただけだと「見にくい」と言われた。濃い面を減らし（1ページ1か所）、文字は黒に近い灰、緑は数字と印だけ、と役割を決めて配置で見せる。
- 明朝の見出しは「キモい」と不評。書体はゴシックで統一する。
- 「全部再構成して」と言われたら、色や細部だけでなく**各ページの配置を組み直す**（`style-plain.md` の「配置の型」）。色だけ変えて「再構成した」と言わない。
- 背景にはクラウド（雲）と IT（回路）のモチーフを控えめに入れると好評。
- 目次 → 導入 → 本題 の順にする。いきなり本題から始めない。
- 各ページの上部の帯は目次と同じタイトルにし、その下に「このページで伝えたいこと」を1文で置く。
- 画像の縦横比を崩さない（引き伸ばさず切り抜く）。
- 推測で書いた内容は、報告で「要確認」としてはっきり伝える。

## 納品前チェック
- [ ] タイトル（plain / cloud では POINT の文）だけを通読して、話がつながる
- [ ] 帯のタイトルが目次の項目名と一致している（plain / cloud）
- [ ] 同じ事実・同じ文が2ページ以上に出ていない（`redundancy_check.py`）
- [ ] 単語の途中・数字と単位の間で改行していない
- [ ] 文字があふれていない・重なっていない・枠に対してスカスカでない
- [ ] 余白・タイトル位置・色の使い方が全ページでそろっている
- [ ] 目立たせたい所が1ページに1か所だけ
- [ ] 数字に単位がある／推測の数字がない
- [ ] PDFの埋め込みフォントが指定どおり（`render.sh` の表示）。Unifont などが出たら、フォントに無い記号を使っている（例：↺ ↻ ✔ は BIZ UDPゴシックに無い。✓ ○ ● ▲ ※ → ①〜⑳ は使える）
- [ ] 動きを外した最終状態だけで内容が伝わる（印刷・PDFを想定）
